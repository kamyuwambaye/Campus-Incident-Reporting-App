# Campus Incident Reporter

A Flutter + Firebase mobile app that lets students report campus issues
(facilities, water, electricity, furniture, sanitation, safety) with photos,
browse and filter all reports, and track each report from **Submitted** to
**In Progress** to **Resolved**. Authorised **staff** accounts review reports
and update their status; students see those updates live.

Built for *Individual Assignment 2: Campus Incident Reporting App*.

| | |
|---|---|
| Framework | Flutter (Dart 3.5+) |
| State management | Riverpod 2 (`Notifier`, `AsyncNotifier`, `StreamProvider`) |
| Auth | Firebase Authentication (email + password) |
| Database | Cloud Firestore (real-time listeners, offline cache) |
| Images | Firebase Storage + `image_picker` |
| Roles | `student` / `staff`, enforced in UI **and** Firestore security rules |

---

## 1. Features

**Students**
- Sign up / sign in / sign out
- Home dashboard: greeting, personal report summary, three most recent reports
- Report an incident: category grid, title, description, campus location + room,
  optional photo (camera or gallery, resized and uploaded to Storage)
- Browse all campus reports with free-text search, status and category filters
- Incident details with status timeline, description, photo and staff notes
- "My Reports" with personal stats and a status filter
- Withdraw an own report while it is still *Submitted*

**Staff** (everything above, plus)
- Campus-wide dashboard numbers
- *Update Status* action on any report (Submitted -> In Progress -> Resolved)
  with an optional note the reporter can read
- Every change is appended to an audit trail (`statusHistory`)

### Architecture (layers)

```
UI (screens/widgets)  -->  Riverpod providers/controllers  -->  services (repositories)  -->  Firebase
        ^                          |
        +---- watch streams -------+   (Firestore snapshots flow back as AsyncValue)
```

- **Screens** never import Firebase. They `ref.watch` providers and call
  controller methods.
- **Controllers** (`AuthController`, `SubmitReportController`,
  `StatusUpdateController`) are `AsyncNotifier`s: they expose
  loading / error state and wrap every write in `AsyncValue.guard`.
- **Repositories** own the Firestore paths, converters and Storage uploads.
- `setState` is only used for ephemeral widget state (selected tab, password
  visibility, selected category in the form).

### Firestore data model

```
users/{uid}
  name: string
  email: string
  role: 'student' | 'staff'      <- can only be changed by an admin
  department: string
  createdAt: timestamp

incidents/{incidentId}
  title: string            (5..80 chars)
  description: string      (20..1000 chars)
  category: 'facilities' | 'water' | 'electricity' | 'furniture' | 'sanitation' | 'safety'
  location: string
  status: 'submitted' | 'in_progress' | 'resolved'
  photoUrl: string | null  (Storage download URL)
  reporterId: uid
  reporterName: string     (denormalised for list display)
  createdAt: server timestamp
  updatedAt: server timestamp
  statusHistory: [ { status, at, byId, byName, note? }, ... ]   <- audit trail

Storage: incidents/{uid}/{timestamp}.jpg
```

Queries used: `incidents orderBy createdAt desc` (all), `incidents where
reporterId == uid` (mine; sorted on device so no composite index is needed),
`incidents/{id}` (detail). Search and filters run on the already-streamed list.

### Access control

| Action | Student | Staff | Enforced by |
|---|---|---|---|
| Read all incidents | yes | yes | rules: `signedIn()` |
| Create incident | own, status must be `submitted` | same | rules |
| Update status / history | no | yes, only those three fields | rules: `isStaff()` + `affectedKeys().hasOnly(...)` |
| Delete incident | own, only while `submitted` | no | rules |
| Change own `role` | no | no | rules: role must equal stored role |
| See *Update Status* button | hidden | shown | `isStaffProvider` (UI) |

`isStaff()` in the rules reads `users/{uid}.role`, so even a modified client
cannot change a status without a staff profile.

## 3. Setup

### 3.1 Prerequisites
- Flutter SDK (stable, 3.24 or newer) and either Android Studio (emulator) or
  Xcode (iOS simulator)
- A Firebase project: <https://console.firebase.google.com>
- Firebase CLI and FlutterFire CLI:

```bash
npm install -g firebase-tools
dart pub global activate flutterfire_cli
```

### 3.2 Generate platform folders
This repository contains the Dart source, tests and Firebase rules. Generate
the Android/iOS runners once:

```bash
flutter create --org com.kamyuwambaye --platforms android,ios .
flutter pub get
```

Then in `android/app/build.gradle.kts` set `minSdk = 23` (required by
Firebase Auth), and in `ios/Runner/Info.plist` add:

```xml
<key>NSCameraUsageDescription</key>
<string>Take a photo of the campus issue you are reporting.</string>
<key>NSPhotoLibraryUsageDescription</key>
<string>Attach a photo of the campus issue you are reporting.</string>
```

### 3.3 Connect Firebase
```bash
firebase login
flutterfire configure        # pick your project, select android + ios
```
This overwrites `lib/firebase_options.dart` and drops the platform config
files into `android/` and `ios/`.

In the Firebase console:
1. **Authentication -> Sign-in method** -> enable *Email/Password*.
2. **Firestore Database** -> create database (production mode).
3. **Storage** -> get started.
4. Deploy the security rules from this repo:

```bash
firebase use <your-project-id>
firebase deploy --only firestore:rules,storage
```

### 3.4 Run
```bash
flutter run
```

### 3.5 Create a staff account (for the demo)
1. Sign up in the app with the staff person's email (it becomes a student).
2. Firebase console -> Firestore -> `users/{uid}` -> edit `role` to `staff`.
3. Sign out and back in (or just wait: the profile is a live stream, so the
   staff UI appears within a second).

Only administrators with console access can do this; the rules reject any
client attempt to write `role: 'staff'`.

## 4. Testing

```bash
flutter analyze
flutter test
```

- `test/validators_test.dart` - form validation rules
- `test/time_format_test.dart` - relative/absolute date formatting
- `test/incident_filter_test.dart` - search/filter logic and dashboard counts
- `test/incident_model_test.dart` - Firestore (de)serialisation round trip
- `test/widget_test.dart` - `StatusChip`, `IncidentCard`, `StatusTimeline`

Manual test matrix (student + staff accounts on an emulator): sign-up
validation, sign-in errors, submit with/without photo, photo > 5 MB rejected,
search/filter combinations, staff status update appears live on the student's
detail screen, student cannot see *Update Status*, withdraw only while
*Submitted*, rules rejected when a student calls `updateStatus` directly.

## 5. Demo video checklist (7-10 min)
1. Sign up as a student, show validation errors, then sign in.
2. Home dashboard; submit a report with a photo; land on its detail page.
3. Browse reports: search, status filter, category filter.
4. Sign out, sign in as staff (show the STAFF badge and campus summary).
5. Open the student's report, update it to *In Progress* with a note.
6. Back on the student account: timeline and staff note updated live.
7. Resolve the report as staff; show My Reports stats changing.
